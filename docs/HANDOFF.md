# Bench Web Plus 当前交接（更新至 2026-11-07）

本文将本次长会话的需求、最终决定、修复、验证证据和未完成项归并交接，不逐字复制聊天。当前源码与本文共同说明现行行为。被替代的预览版说明与分散验收文档已从当前源码树删除；历史演进可查 Git 提交，不再作为安装入口。

不公开实际服务器地址、登录信息、指纹、个人路径、任务编号、管理员 Cookie、token、密钥或原始运维归档。地址示例仅使用文档保留网段；部署步骤见 [README](../README.md)、[共享中心部署](SHARED_CENTER.md)和[排障](CENTER_TROUBLESHOOTING.md)。

## 交付目标与架构

- 从原 ascend-bench-web 的单机工作台演进为一个共享中心、多位管理员与匿名普通用户、多台受管 Runner。
- 中心在常开电脑提供 HTTPS、账号、清单、互锁和结果转发；SSH 用于部署维护，受限 TLS API 用于日常评测管理；Runner 内 AISBench 直接请求模型服务，不逐条经中心或 SSH 代理推理。
- 新建中心只需 Python、源码与固定 Runner 包；其他电脑只需浏览器。无需 Node、前端编译、NPU、Docker 或模型权重安装在中心电脑。
- Runner 是 CPU 客户端，不自动拉起 vLLM、不安装/下载模型。跨机测试允许，只要 Runner 能访问目标 HTTP 服务并读取 tokenizer。
- 凭据不在仓库。首次 SSH 密码只在本次内存会话使用；后续专用密钥和签名授权留在中心受保护数据目录。普通用户无 SSH、部署或存储清理权限。

## 会话需求与最终处理

### 中心部署、账号与常驻

1. 首次向导选择固定 HTTPS 地址、明确用户网段、独立管理员账号及证书；普通用户免登录，管理员各自登录。
2. 修复 Windows 商店占位 Python、缺失 `py`、PowerShell 引号路径缺少 `&` 的说明；`FLEET_PYTHON` 只指定解释器，不会创建 `py` 命令。
3. 登录任务与 SYSTEM 开机任务分开。默认向导建立当前用户登录任务；需无人登录开机运行时，以管理员权限运行独立安装器，复制到受保护 ProgramData，不从可编辑工作区以 SYSTEM 执行。
4. 修复计划任务 XML 的非法 `ServiceAccount` 值、控制台编码与 SID 归属核对；先用 Windows 校验 XML，再复制和注册；停止后等待端口释放，不强杀未知进程。
5. 更新开机中心必须重新安装受保护副本。保留其真实运行数据和账号，不从旧工作区覆盖新授权。不能仅 git pull 工作区就宣称运行中心已更新。
6. 多电脑管理员浏览器共享的是中心授权，不是浏览器本机 SSH。新电脑另建中心不能直接复用其他电脑的 DPAPI 授权。

### SSH 自动管理与重启恢复

1. 首次核对主机指纹和密码授权后，使用专用密钥、签名脚本和来源约束，断线退避重连，中心重启恢复；不保存服务器密码、不读个人私钥或 ssh-agent。
2. 没有“连接几天后必须重新输入密码”的固定期限。授权撤销、指纹或中心来源改变时必须核验，不能自动绕过。受限组件证书也有有效期，不等于永久免维护。
3. 服务器安装独立恢复服务，只恢复登记且容器 ID、文件哈希匹配的组件；外部容器主动停止不擅自启动。工具新容器的重启策略也不能绕过管理员 `docker stop` 意图。
4. SSH 管理正常与 Runner API 正常分别展示。SSH 重连不自动重复发送“结果未知”的部署命令，避免实际已执行又安装第二遍。
5. 修复大包传输超过签名管理通道消息限制的问题，使用分块、分块摘要、最终摘要与原子发布；中断不重放不确定写入。

### Runner 安装、换容器与目录隔离

1. 已停止的专用旧容器可由管理员手动停止/删除，再按正常流程选新容器复用端口和安装路径；移除“释放并替换旧 Runner”操作入口。
2. 安装核验旧容器确实停止/删除、没有宿主 PID、端口无未知监听、路径挂载可写。失败回退程序和配置，旧容器保持停止；不会把未知端口当旧 Runner 杀掉。
3. 新增并存 Runner 必须独立 Runner 端口、受限连接端口及持久目录；核验宿主挂载，避免不同容器路径实际共享一个可写目录而互相破坏。
4. 修复容器列表把所有容器误标“已安装”、过期部署记录阻断新部署、旧登记身份与实际容器不符的问题。最新代码是中心所带固定包的版本，不是每次自动追 GitHub main。
5. `ais_bench` 文件存在但报 ENOENT，通常是 shebang 或虚拟环境 Python 链接指向旧容器。当前实际执行检查，不只看可执行位；环境与可编辑源码按完整容器 ID 放到 `environments/<容器ID>/`，避免 A、B 共享失效虚拟环境。
6. 选择可用 Python，验证 venv/ensurepip、tokenizer 导入及线程能力；兼容老 Docker 对 clone3 的限制，不放宽 seccomp 或启用 privileged。
7. 新容器只读挂载 `/mnt`、`/home`，项目目录单独 RW。已有容器无法动态增加挂载，须由管理员规划迁移。tokenizer 不可见时保留存在性检查并提示检查 `/mnt` 路径，不在输入框下面额外加说明。
8. pip 的“找不到 nltk”可能实际是企业 CA 校验失败，不把它解释成依赖版本不存在。提供可信源/CA处理，保留失败原因，不全局关闭 TLS 验证。
9. Runner/评测 API 进程使用 CPU tokenizer，禁用可选 NPU 后端自动加载，保留底层异常链。若模型服务返回 EngineCore 500，需要查服务日志，不能归为 SSH 故障。

### 状态刷新、任务结束与界面

1. 放弃固定每 3/10/30 秒采集方案。点击刷新实时查询或合并同一轮查询；完成后缓存窗口按最近成功平均耗时的两倍向上取整，1–10 秒，无样本暂用 3 秒，缓存命中不续期。
2. 不可用节点保留清单且不可选；多节点失败不串行拖住全部健康节点。故障重连独立退避，正常网段不应因另一网段下电而无法选择。
3. 选择、提交仍核验真实状态和占用。任务完成后确认进程组退出，僵尸进程不算活跃测试；正常自动释放，未知或仍有活跃子进程保持占用，刷新再核验，不让管理员日常手工清 busy。
4. 执行页显示 Runner 和目标服务身份，避免只看目录不知哪台。结果文件折叠区不因轮询不断重建而关闭。
5. 数据生成独立子进程和异步状态，HTTP 线程不承担完整生成；多页刷新能恢复本会话生成状态，而不是把数据准备中误报为可选空闲。
6. 中心重启/匿名 Cookie 过期可能使旧选择失效，需重新选择或管理员接管；目前没有完整的匿名跨会话任务恢复保证，也未把所有浏览器切页场景都当作已验收。

### AISBench 原生行为与参数最终约定

1. 以配套固定 AISBench 源码为准，不宣称支持上游任意未来版本。并发进入 `models[0].batch_size`，不再加不被该版本接受的 `--batch-size`。
2. 最大输出支持 225280 tokens（220 Ki），并发可填 1000；这是配置范围和透传能力，不代表已真实运行 1000 并发或生成 220k 输出。
3. 温度不额外固定为 0–2，按非负数透传，具体合法范围由目标模型服务决定；额外生成参数同样取决于服务支持。
4. `max_model_len` 按 AISBench/服务原生行为，不截断/填充精度题目，不在 Runner 额外加入上下文长度拦截。性能输入长度由 tokenizer 生成与校验，服务模板差异造成的实际 token 数变化只提示。
5. Chat 与 Completions 使用对应原生 API 模型类；流式、温度、ignore_eos、输出、并发、请求超时和 retry 写入真实执行快照。服务不支持某字段不等于工具能替它实现。
6. 预热 0–正式样本总数，默认最大输出跟随正式输出，可独立修改。性能使用独立预热输入避免污染完整正式提示缓存；预热不计正式评分和吞吐。单独预热输出通过明确运行时适配实现，不虚构为上游通用 CLI 参数。
7. 超时默认 `native`，保留配套 AISBench 原生 None 不限时；历史 `AIS_BENCH_TOTAL_TIMEOUT=None` 同样表达不限时，但当前 native 不替换原生超时对象。自定义秒数同时作用预热/正式每次请求。
8. 网页 retry 原值透传，不再做额外重试数加一转换。连接异常时修复未唤醒的流式读取等待，回到原生重试路径，不给不限时模式暗加总 deadline。
9. 页面仅精度 `all`、性能 `perf`，额外参数禁止覆盖 mode；`perf + reuse` 保留 AISBench 自动转 `perf_viz`。旧版六模式验收不代表当前页面仍提供六个选项。
10. 稳态指标使用原生 `StablePerfMetricCalculator`；pressure 与其独立，按时长循环请求。样本少、请求持续形态不满足会报 CALC-DATA-002，不造稳态窗口，也不保证固定“请求数/并发比”必成功。
11. 额外参数说明分三类：models 顶层、generation_kwargs、CLI；名单从前端 registry 生成，不换行堆说明。已在表单的参数不允许额外覆盖；未收录生成字段用 `generation_kwargs.字段=JSON值`，不开放任意模型顶层/CLI透传与任意代码。
12. 常见 top_p/top_k、惩罚、skip_special_tokens 可直接填；reasoning_effort、chat_template_kwargs 仅模型服务支持时有意义，不宣称所有模型均支持。
13. 当前任务状态遵循原生退出码：退出 0 但失败请求/缺评分时保留原生状态并显示提示；不再以网页二次判定改写原生成功/失败。早期“失败一条即网页失败”已被后续要求替代。复核须看失败文件，不能把完成当作全部请求成功。

### 数据生成、缓存与互锁

1. 性能生成支持 0–100% 共享前缀、随机种子及大输入、大条数；逐条流式写入、有界流水线、临时文件校验后原子发布，避免把所有长文本堆进内存。
2. 缓存键不仅是目录可见名：还包括输入/输出、请求数、种子、比例、接口、tokenizer/模板指纹及缓存版本；参数看起来相同但指纹不同会重建，不盲目复用旧格式。
3. 复用要验证完整 manifest、条目数与长度；只读同一 tokenizer 无需互锁，共用缓存目录写入才需要跨进程/共享文件系统锁，不能按“能看到同目录”就推断所有 Runner 缓存都同一位置。
4. 2026-11-08 用户确认：不同 Runner 可以同时为同一服务生成数据集；生成只在客户端读取 tokenizer、使用 CPU/磁盘，不占用模型服务推理锁。每个 Runner 仍只允许一个操作，生成期间不能切换服务或启动测试；共用缓存目录另有跨进程/共享文件系统写锁，不同缓存参数不写同一成品目录。真实测试继续由中心服务占用与 Runner 执行锁保证一对一。多 Runner 同机生成仍会竞争 CPU、内存和磁盘，目前没有按用户/主机的生成资源配额。
5. 中心锁只覆盖本中心管理的任务，无法自动发现和阻止所有独立原生 CLI、其他中心或外部用户。运行压力测试前仍需实际检查现有进程与资源。
6. 数据集目录发现 Hugging Face/ModelScope 任意数据并自动适配尚未实现。将原始文件复制进 datasets 不意味着自动形成正确 AISBench 配置、题型、模板和评分器。

### 日志、结果、存储清理

1. 以 AISBench 原生输出为主。最终默认 debug 原生 Warmup、Progress、POST/RECV/FAIL/FIN，统一到一个执行日志区；不再伪造 `[AISBench progress: ...]` 进度。
2. 非 debug 场景读取真实子任务日志/终端输出；不把任务总数 1/1 误当题目条数。pressure 以时间显示进度属于原生模式，不改为固定题数。
3. 日志读取改为有界尾部/增量采集，不每次轮询读取完整文件。网页显示尾部不是完整日志被截断；本地执行日志、config.py、run.sh 和结果保持完整。
4. 原生表格保留原文，撤销拆表/重排导出方案。比例字体与自动折行可能让纯 log 线框错位，原生 CSV/HTML 可用于阅读，不修改指标内容。
5. 每个正式任务保存配置快照、真实 argv、环境与复现脚本。脱离 run.sh 只复制裸命令未必复现超时、预热和运行时适配。
6. 放弃后台每日自动清理和额外轻量历史库；管理员手动扫描所有 Runner、选保留天数、默认全选可取消，再删除。删除整个正式任务目录后从测试记录消失。
7. 清理仅过期 `datasets/perf` 与 `results/jobs/real-*`，不任意删环境、备份、非正式目录、模型和他人容器。性能缓存最近生成/校验复用触碰 `.last-used`；任务使用 reader 标记保护。结果按结束时间与内部最新修改时间较新者，查看/下载不刷新。
8. 扫描不等于立即删除；删除时重验状态、锁、签名、指纹。正在测试/生成、SSH 或 API不可用、未知占用、目录变化、符号链接/挂载点均拒绝或跳过，不凭旧扫描结果强删。
9. 历史自测临时目录按明确白名单归档清理；正式任务及有效缓存按保留策略处理。后续自测同样不要留下无人知道用途的大目录。

## 验证证据与不能宣称的事项

- 早期实机验收覆盖停止/删除/换容器、跨机测试、三精度数据集小批量、GPQA Diamond 全量 198 题、性能选定小批量和原规模任务。实机结果的关键范围已归并至本节；不再分发与当前行为不一致的早期验收文档。
- 曾用真实中心 HTTP 接口完成 2560 条 × 131072 输入、1024 输出、90% 共享前缀的冷生成，约 542.8 秒；再次校验复用约 2.7 秒。不是浏览器逐项点击测试，也不是所有机器都必达同耗时。
- 早期 240/320 并发规格有缩小样本验证，不能宣称全部高并发与全部阈值已通过。长输出上限配置提交成功不代表实际生成等量 token。
- 先前报告曾写七台已更新；这是对应时间点的实机状态，不是本仓库永远保证远端在线或版本最新。新中心/更新中心后仍需核验实际登记节点；本次文档与源码发布未重启生产服务。
- 独立服务的超时/断连、失败恢复、互锁、清理与日志有本地回归；真实模型服务返回 500、连接拒绝、服务端排队/超时必须区分，不能统一归为工具或 SSH 不稳定。
- AISBench 对照报告现已匿名化，详见[实验报告](experiments/2026-11-07-aisbench-tool-native-ab.md)。单向 1024 观测吞吐差 −0.25%、ITL +1.2 ms；追加并行平均 −4.75%，但原生重复自身波动明显，未定位因果。不能称固定工具损失或所有指标完全无影响。
- 最初三个完整双向拓扑未全部执行，不记作通过。追加 ABBA 使用每路 128/256，尚不足统计显著性结论；中心真实 API 提交不冒称鼠标操作浏览器。

## 本次发布前检查与新增修复

- 发布前运行全体 Python 回归 209 项，通过（1 项因当前 Windows 无创建符号链接权限而跳过），前端 14 个 CJS 回归脚本通过；Runner 包的 42 个运行文件摘要、三个 wheel 的 ZIP/CRC 和原始字节一致性通过。完整分发包通过 ZIP/CRC、排除项、源码与内置运行包匹配、全新目录解压与隔离 Python 导入自检。这些检查不连接或重启生产模型服务。
- 发布检查发现构建器对 wheel 也执行 CRLF 转换，损坏二进制；改为仅对已知文本扩展规范换行，增加二进制新建/替换包回归，并从原始 wheel 重建包。
- 清理测试夹具的过期返回类型：性能数据路径使用真实临时 Path，符合新缓存 reader 标记流程，不去掉生产缓存保护来迎合旧 mock。
- 不发布机器专用 tools、密码、连接配置、数据库、原始日志、实验归档或模型。少量 wheel 在仓库，完整离线依赖另备；当前 Runner 包约 39 MB，旧 7 MB 说明不再适用。

## 后续维护约束

1. 修改 overlay 后必须重建 dist 与 SHA256，否则管理员部署的是旧 Runner。更新中心运行副本与空闲远端 Runner 是两个步骤。
2. 不覆盖中心数据，不跨用户/机器盲迁 DPAPI；备份需保护，GitHub 只发布脱敏材料。
3. 参数新功能需同时核对前端 registry、Runner validate/make_config、CLI能力与运行时环境；优先复用原生，不增加未说明的限制或转换。
4. 实验前检查外部任务、资源和目标服务真实可用性；不动他人容器/vLLM，不清共享缓存。要停止未知服务必须先取得明确授权。
5. 运行中任务不为升级/清理强停。结果未知不能凭时间过期释放锁或重放部署；状态恢复与真正可再次执行是两件事。
6. README 是新中心入口，本文是唯一当前交接；部署与排障文档通过文档索引访问。新增功能应同步更新这些入口，不重复保留互相冲突的说明。
