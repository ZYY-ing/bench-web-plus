# 多用户、多 Runner 并行与持续补位测试报告

实验日期：2026-11-08。本文沿用实验报告的匿名方式，使用机器 A、B、C、D 和服务代号，不公开真实地址、端口、账号、模型路径、容器标识及任务标识。原始日志、截图和任务映射保留在本地归档。本文依据已完成记录整理，没有为撰写报告追加推理压测。

机器代号仅在本文内部有效，与前一份对照实验独立映射。

## 结论

共执行 **60 次测试任务**，实测达到 **5 个 Runner 同时运行**。后期按要求改为持续补位，每路完成后独立检查和接续，不再等待整轮结束。

- 60 次任务原生退出码均为 **0**，推理失败请求均为 **0**；已核验配置未发现偏差。
- **2 次 AIME2026 缺失精度分数**：原生数学答案后处理抛出异常，但 AISBench 仍以 0 退出。不能将本次结果判为全部通过。
- 持续补位阶段记录 **42,644 次刷新/清单查询，错误 0 次**；290 次并发状态采样中未发现运行任务的服务目标重叠。
- 观察到同服务的跨 Runner 并行生成、刷新后需重填配置、安装包内 wheel 损坏，以及一次管理 challenge 请求失败。用户后续确认前两项符合预期；评分、安装包和管理请求的后续核查见下文。
- 结束后五个 Runner 均健康空闲，60 条本次任务记录均可回读。临时模型服务已停止，Runner 和测试归档保留。

## 测试方式与范围

批量并发使用 **15 个独立 Cookie 会话**调用中心实际 API，随机进行 Runner 状态刷新和清单查询，并执行精度、性能混合任务。IP 用作模拟用户标签，实际 TCP 来源地址没有改变。

另通过真实浏览器完成了 GPQA 以及性能数据生成、提交、执行和历史回读流程，并检查运行中刷新、同一用户打开第二页面的行为。批量 API 提交与浏览器逐项点击分开记录；本次不是 15 个真实来源 IP 的完整浏览器压测。

日常评测管理使用受限 TLS API，推理请求由 Runner 直接发往模型服务。本次没有覆盖推理 SSH 隧道的故障切换；SSH 用于部署和只读管理预检。

## 资源选择与安全检查

测试前检查现有测试进程、CPU、内存、NPU、网络，以及服务健康和请求计数。通过间隔探测判断服务是否空闲，遇到他人任务时跳过或等待，不强行发压。

- 12 个候选地址进行了 SSH 连通检查；其中 8 台具备现有管理授权，可进行相应资源检查。其余 4 台没有授权会话，未在其上进行资源探测或推理。
- 跳过检测到外部测试请求或外部精度任务的服务。
- 确认一个候选节点是服务 A 的分布式 worker，没有把它误计为另一套独立模型服务。
- 部分跨网段 Runner 无法访问另一网段服务，因此采用同网段可达资源，没有修改路由或防火墙。
- 在空闲加速资源上建立两套本次专用的单机 8B 模型服务；新增一个 CPU 专用 Runner，使用独立容器、安装目录和端口，不分配 NPU。
- 没有停止、重启或修改他人的容器、模型服务，没有清理共享服务缓存。

## 调度过程与补位

前期完成环境探测、试跑、冲突探测和按轮并发。改为持续补位时已有 **36 次提交**；新调度器接管当时的在途任务，再新增 **24 次**，总计 60 次。只切换了本次本地调度进程，已经提交的远端测试继续运行。

每条通路独立执行：

1. 等待当前任务原生结束并刷新状态。
2. 取得进程退出证明，复核 Runner 和目标服务资源。
3. 选择下一用例，检查连接，生成或校验复用数据集。
4. 再次检查后单次提交新任务，不设置全局轮次屏障。

记录到 **23 次补位**：从退出核验完成到下一次提交，中位 **19.94 秒**，最短 **12.72 秒**，最长 **45.56 秒**。该时间包含后续资源检查和数据准备，不包含此前的完成轮询、退出核验时间；需要冷生成长数据时会更久。

600 秒表示停止继续发流的时点，之后仍等待已发请求返回。长上下文任务的总耗时可能超过 600 秒，没有据此强行终止任务。

## 发现的问题

### 1. AIME 原生评分异常：退出 0，但没有分数

7 次 AIME2026 中有 2 次缺失评分。日志显示 `math_postprocess_v2` 在解析不符合要求的 `\boxed{…}` 答案时抛出 `AISBenchDataContentError / DSET-DATA-002`，汇总表中的指标为横线、accuracy 为 null。

这两次推理失败请求为 0，原生进程仍以 0 退出。记录保留原生状态，但评估结果应标为评分不完整，不能视作完整通过。本次未修改官方评分器。

后续只读核查了保存的原始预测，并离线重放当时原生数学后处理函数：两批各 16 条均标记推理成功，每批恰有一个回答触发相同异常。一个回答包含 `\boxed {50 + 12}`（命令和左括号间有空格），另一个包含畸形 `\boxed` 片段；提取器找到片段后，`remove_boxed` 严格要求 `\boxed{` 并抛出异常。两条异常回答输出分别为 3,181 和 2,358 tokens，均低于 4,096 上限，因此不能归因于达到输出上限。

两批均来自临时 8B 服务 D1；同服务还有 3 批正常产出 0/16 分数，既有服务 B 的两批均为 9/16。这支持“模型输出格式触发原生评分器异常”的直接原因，没有发现请求失败证据，但不足以判断模型数学能力差是否还受服务推理数值问题影响。要核查后者需要同权重、同配置的参考后端对照；本次没有重新拉起服务或追加推理，也没有改写官方评分规则或历史分数。

### 2. 同服务、多 Runner 并行生成：用户确认符合设计

用户后续明确：允许不同 Runner 为同一服务同时生成数据集。该行为保留，不增加服务级生成互斥。

源码与隔离 HTTP 回归确认：生成读取本地 tokenizer，不发模型推理请求；同 Runner 使用操作锁，相同生成请求复用进度、不同请求返回 409，生成期间切服务或测试也返回 409；共用成品目录使用跨进程及共享文件系统写锁，临时文件验证后原子发布。真实推理仍使用中心 Runner/服务占用保护。

多用户接入的剩余风险主要是资源公平性：不同 Runner 同机生成可叠加 CPU、tokenizer 内存和磁盘/NFS I/O；当前只有单 Runner 限流、流式/有界生成及单次磁盘空间检查，没有按用户/主机的总资源配额，也没有为同时生成统一预留磁盘空间。普通用户仍可能反复占用空闲 Runner 或填写很大的合法参数，使他人等待或使生成因资源不足失败；不能承诺任意用户规模下零影响。这不等于会写坏共享 tokenizer 或重复启动模型推理。

### 3. 数据生成完成后刷新，参数不能恢复

用户后续确认这是预期行为，刷新后由用户重填，不安排持久化修改。

真实网页完成 16k/1k、64 条、公共前缀 100% 的数据生成后刷新：连接变回未验证，条数恢复为 32、并发恢复为 1、输出上限恢复为 2048，公共前缀和持续压测开关复位。重新检查连接也没有恢复这些参数。

生成文件仍在，重新填写相同参数后显示校验复用成功。没有按复位后的默认值提交推理。该现象针对生成完成后的表单持久化，本次没有据此认定正在准备中的生成任务无法恢复。

### 4. 运行中刷新、多页面没有自动恢复进度页

用户后续确认接受当前刷新行为，不安排自动恢复修改。后台互斥和原任务状态仍需保持。

刷新正在执行的页面、或同用户在第二页打开同一 Runner，均返回配置页，没有自动恢复进度页，并一度显示缓存的空闲状态。后台原任务仍在运行。

手动刷新状态后，网页正确显示忙碌并禁用配置；历史记录能查看原任务，未产生重复任务。测试结束后，所有 60 条本次任务记录均可回读。

### 5. 安装包中 NLTK wheel 已损坏

新增 Runner 初次安装失败，wheel 解压出现 `-11` 的非法偏移。包内 wheel 比有效文件少 11 字节。上传归档的完整 SHA256 与中心期望一致，归档内就包含同一损坏文件，损坏发生在提取进新 Runner 之前，不是本次上传丢包。

处理方式：只向新增 Runner 的私有目录放入校验通过的 wheel，离线安装依赖，随后通过正常管理员部署完成接入。既有 Runner 环境和共享缓存未改动，中心原安装包未在本次测试中替换。

后续核查确认，当前仓库分发包已是修复过二进制换行转换的版本，三个内置 wheel 均通过 ZIP/CRC，NLTK 与 overlay 原始字节一致，大小为 1,510,158 字节；旧包中为 1,510,147 字节。将当前分发包中的 NLTK 解出后，在隔离临时目录执行 `pip install --no-index --no-deps --no-cache-dir --target ...` 成功，没有改动现有 Python/Runner 环境。此次又给构建器增加所有内置 wheel 的 ZIP/CRC 发布前校验，以及坏源包/坏 overlay 都不能覆盖已发布包的回归。

当前仓库安装包 SHA256 为 `f201569483cd63388998b2c19362aaccf890fdbaa3173122274b5738dc0ecd81`。中心 ProgramData 副本不随 Git 更新自动同步，当前执行身份无权读取/替换；已准备管理员安全同步工具，先验证源包和全部 wheel，再检查部署记录，发现进行中或结果未知部署则不替换。同步只更新安装包及其摘要，不部署或重启任何 Runner，也不修改共享包缓存或已有离线接入包。已有离线接入包若携带旧坏 wheel，需重新生成，不能靠更新中心包追溯修复。

### 6. 一次管理 challenge 请求失败：疑似文件竞争

一次只读预检在获取 challenge 时失败：枚举到的 challenge 文件在随后访问时已不存在。远端预检脚本当时尚未执行，推理任务尚未提交；随后重新进行只读检查成功。

challenge 是管理协议用于防重放的一次性随机值。中心取得它后，对“challenge 加管理脚本”签名；服务器验证签名、时效并消费该值后才执行脚本。正常消费会删除对应文件。

结合 [management_host.py](../../fleet/management_host.py) 的代码，可能的时序为：

1. 请求甲枚举 challenge 目录，确认某文件存在。
2. 请求乙正常消费该 challenge，删除文件。
3. 请求甲继续调用该文件的 `stat()`，遇到 `FileNotFoundError`。
4. 清理循环未逐项容忍此异常，导致请求甲的新 challenge 获取失败。

消费端使用 `challenge.lock`，清理遍历未使用同一锁，文件存在检查与读取之间也不是原子操作。**这是依据报错和源码提出的根因推测，尚未进行受控复现。** 本次没有证据表明 SSH 授权被撤销，也没有将其归为推理 SSH 隧道崩溃。

后续可考虑让清理与消费共享锁，并逐项处理文件已消失的情况，同时保留签名验证、有效期和单次消费校验。本次没有部署该修复，也没有重放结果未知的推理提交。

#### 后续修复与验证（2026-11-08）

验收结束后，已针对该问题修复 [management_host.py](../../fleet/management_host.py)：challenge 的创建、过期清理和消费共用原有文件锁；清理时逐项容忍文件消失，消费时文件消失则拒绝执行。签名、有效期和执行前单次消费规则保留，没有增加部署或测试的自动重试。锁在启动管理脚本前释放，不覆盖整个部署过程。

新增 [回归测试](../../fleet/test_management_host.py)，本地管理测试共 22 项，其中 18 项通过、4 项 Linux 专用测试跳过；随后在隔离临时目录中使用真实 Linux `flock`、OpenSSL 和子进程完成全部 5 项 broker 测试：

- 同一签名请求并发提交 32 次，脚本和审计均仅执行/记录 1 次，其余拒绝。
- 12 个不同请求消费 challenge，与 32 个新 challenge 发放、80 个过期文件清理混合并行，全部成功。
- 篡改签名内容、过期、缺失、符号链接 challenge 均不执行脚本。
- 管理脚本仍在运行时，其他请求可以取得新 challenge。
- 人为制造文件在存在检查后消失，清理仍成功，并检查使用共享锁。

另保留现有“连接中断不重放”“未收到退出状态视为结果未知”测试。这里保证的是同一 challenge 的请求至多执行一次；不将不同 challenge 的独立人工提交视为同一操作，也不声称通信故障时任务一定执行成功。

8 台已有管理授权的机器已逐台完成哈希校验、备份和管理脚本原子替换，随后通过新管理请求校验。更新前后运行中容器的 ID、启动时间、PID、重启计数一致；未提交实际部署/推理，未重启中心、Runner、容器或模型服务，也未清理共享缓存。中心 ProgramData 中用于未来新授权的模板受管理员 ACL 保护，由用户随后确认已执行管理员复制；无需重启中心。后续再次只读复核 8 台授权机器，脚本哈希均匹配修复版、签名管理请求均成功。原始故障的具体竞争请求仍无法从已有日志确定，以上受控验证不代表追溯确认了当时的请求身份。

管理员目前没有独立删除部署历史的接口。直接删数据库中已完成/失败的部署记录不会自行停止容器或删除测试结果，但会丢失部署日志及部分已安装环境识别线索；运行中或结果未知的记录还参与任务占用保护与结果核对，不能通过删除记录解除。界面“移除 Runner”仅移出接入列表，保留远端进程、文件和结果；它与删除部署历史、清理数据文件是不同操作。

### 7. 执行工具的时序限制

浏览器控制动作曾耗时约 21 秒，出现 Runner 选择资格过期和读取页面状态超时。后续核对确认部分操作实际上已成功，不能将控制工具超时直接视作产品崩溃。

早期第五路重叠负载使用 API 提交；随后另行完成了真实网页性能生成、提交、执行及历史完成状态核对，该网页任务退出 0、失败请求 0。

本次已验证持续补位调度、正常任务执行、针对性推理冲突拒绝及历史回读。后续用户确认跨 Runner 同服务生成和刷新重填属于预期；challenge 已修复并复核 8 台授权机器均为修复版本，用户确认中心模板已同步。当前重点为评分缺失的原生兼容性、生成资源公平性，以及将已验证的安装包同步到受保护中心副本。此次相关回归 73 项中 69 项通过、4 项 Linux 专用测试跳过（已在上一轮 Linux 实机验证）；另对安全同步工具的正常更新、重复执行、忙碌/未知部署拒绝和源包哈希不匹配完成隔离验证。
