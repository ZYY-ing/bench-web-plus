# bench-web-plus 与原生 AISBench 对照实验

实验日期：2026-11-07。本文只使用 A、B、C 机器代号，不公开实际地址、端口、账号、安装目录和任务标识。所有指标来自已完成的实验，没有为改写报告追加压测。

## 结论

**本次没有证明工具造成了固定比例的推理性能损失，也没有证明工具完全零开销。**

- 1,024 条单向对照：工具比原生的输出吞吐低约 **0.25%**；平均 ITL 高 **1.2 ms**，平均 TTFT 高 **49.2 ms**。这是一次顺序配对的实测差值，尚不能判断差异来自工具还是运行波动。
- 追加并行对照：工具两轮平均输出吞吐比原生低 **4.75%**，但原生自身两轮结果也明显不同，不能把这 4.75% 直接当成 Runner 开销。
- 对同时被测的 B 本机 vLLM：本次重叠时间内没有观察到吞吐降低；其中一轮 TTFT 比基线高约 **129 ms（7.50%）**。请求集合及采样窗口不同，尚不能确定这项延迟变化由工具引起。
- 能观察到工具的额外控制工作和资源消耗，但**导致推理指标差异的具体原因尚未定位**。现有证据不足以认定是 Runner、网络、服务调度或缓存中的某一项。

## 实验前提

A、B 均运行 vLLM；C 用作测试客户端。A、B 的模型部署配置存在差别，因此只比较同一路、同一目标服务使用两种方法的结果，不用 A、B 之间的绝对吞吐判断工具影响。

测试前检查服务可用性、现有测试进程和机器资源。所选资源具备运行条件；追加场景中 B 平均宿主机 CPU 使用率约 8.6%～9.0%，内存余量充足，测试客户端没有分配 NPU。没有停止、重启或修改他人的容器与服务，没有清理共享服务缓存。

两种方法的区别：

| 方法 | 实际执行方式 |
|---|---|
| 工具 | 调用网页使用的真实中心 HTTP API 提交，由已部署 Runner 启动 AISBench，每 5 秒读取结果。未操作浏览器逐项点击，未测浏览器渲染开销。 |
| 原生 | 在独立 Python 环境直接执行官方 AISBench CLI，不加载工具运行时注入；该阶段只暂停本次已确认空闲的专用 Runner 执行进程，结束后恢复。 |

AISBench 固定为官方 3.1.0，对应[源码提交](https://github.com/AISBench/benchmark/tree/7bcb6440da11bef020943b2af9ed7c1ac8362306)。工具内置与原生对照的 1,076 个 Python 文件逐一校验一致；Python 和依赖版本对齐。老 Docker 的 clone3/seccomp 兼容条件在原生启动器中独立对齐，不修改 AISBench 请求与指标算法。原生组仍保留 SSH 管理和同样的资源采样，因此不是整机完全无后台管理进程的对照。

控制参数如下；仅执行文件、配置文件、输出文件所在位置不同，并按用户授权每轮使用独立 cache_salt，避免后一次直接复用上一次完整提示缓存。不清空服务端共享缓存。

| 参数 | 对照值 |
|---|---|
| 正式输入 / 输出 | 16,384 / 1,024 tokens |
| 共享前缀 | 90%；这是数据配置，不是声称服务实际命中率必为 90% |
| 最大并发 / request_rate | 32 / 0 |
| 预热 | 5 条，最大输出 1,024，不计入正式请求 |
| temperature / ignore_eos / seed | 0 / true / 42 |
| 接口 / 响应 | Chat Completions / 流式 |
| 模式 | perf；pressure 关闭，稳态汇总关闭 |
| 超时 / retry | AISBench 原生不限时 / 2 |
| debug / max_num_workers | true / 1 |

数据文件逐字节一致；同一路的模型配置与执行参数一致。命令结构为：

```bash
ais_bench config.py --mode perf --num-prompts 1024 --num-warmups 5 --work-dir output --max-num-workers 1 --debug --dump-eval-details
```

并发在 `models[0].batch_size=32` 配置。追加测试只按下面说明调整正式请求数，其他控制参数一致。

## 实验一：单向 1,024 条完整对照

C→B，先工具、后原生，各执行一次。两次均预热 5 条成功，正式 1,024 条成功、失败 0，正式输入与输出长度一致。

| 指标 | 工具 | 原生 | 工具相对原生 |
|---|---:|---:|---:|
| Benchmark Duration | 2340692.824 ms | 2334793.186 ms | +0.253% |
| Output Token Throughput | 447.9768 token/s | 449.1087 token/s | -0.252% |
| E2EL | 72634.5 ms | 72501.1 ms | +0.184% |
| TTFT | 1820.2 ms | 1771.0 ms | +2.778% |
| TPOT | 69.2 ms | 69.1 ms | +0.145% |
| ITL | 168.9 ms | 167.7 ms | +0.716% |

工具从提交 API 到观察到完成约 2,417.25 秒；原生命令执行约 2,399.59 秒，相差 17.66 秒。两者起止边界不同，包含检查、启动、预热、汇总、结果收集及轮询等待，不能把这 17.66 秒全部算作推理开销。

## 实验二：B 测 A，同时 C 测 B

```text
B 的 Runner / 原生 AISBench ──→ A 的 vLLM
C 的原生 AISBench          ──→ B 的 vLLM
```

B 同时做两件事：向 A 发测试请求，并让本机 vLLM 接收 C 的测试请求。第一路比较工具与原生，第二路模拟另一个人正在测试 B，用来观察是否相互争抢资源。

B→A 每轮正式 128 条，C→B 每轮正式 256 条，以覆盖第一路运行时间。顺序为工具—原生—原生—工具。数据集提前生成，不把大数据集生成混入两路并行推理。每轮两路均预热 5 条成功、正式请求全部成功；服务请求增量与正式加预热数量吻合，未发现额外请求。

### B→A：工具与原生的正式结果

| 轮次 | B 的执行方法 | 输出吞吐 token/s | TTFT ms | TPOT ms | ITL ms |
|---|---|---:|---:|---:|---:|
| 1 | 工具 | 794.8768 | 3351.1 | 37.0 | 46.6 |
| 2 | 原生 | 881.2339 | 2307.4 | 34.0 | 43.6 |
| 3 | 原生 | 780.9005 | 2738.0 | 38.3 | 50.5 |
| 4 | 工具 | 788.2938 | 2349.1 | 38.3 | 48.6 |

两轮平均输出吞吐：工具 **791.5853**、原生 **831.0672 token/s**，工具观测值低 4.75%。平均 ITL：工具 **47.60 ms**、原生 **47.05 ms**。

但原生两轮吞吐分别为 881.2339 和 780.9005，工具分别为 794.8768 和 788.2938。原生自身波动已经大于两种方法的平均差距；每种方法只有两轮，无法可靠分离运行波动与工具影响。

### 本机服务被测，会不会影响 B 测 A？

并行测试后，另做 B→A 单独运行的对照，工具与原生各 128 条一次，此时 B 的本机服务没有请求增量：

| B 的执行方法 | 只有 B→A 的输出吞吐 | 同时有 C→B 时的 B→A 平均输出吞吐 | 相对变化 |
|---|---:|---:|---:|
| 工具 | 769.6345 | 791.5853 | +2.85% |
| 原生 | 804.8254 | 831.0672 | +3.26% |

本次没有观察到 B 本机服务承受负载后，B→A 的吞吐降低。小幅上升按运行波动看待，不解释成并行测试有益。这测量的是 B→A 整条路径，不能据此证明 A 的内部性能在所有条件下都不变。

### B 去测 A，会不会拖慢 B 本机的 vLLM？

比较 C→B 单独运行，以及同时存在 B→A 时，B 的服务表现。

“重叠时段”指两路都在进行正式请求的一段时间；避开最后请求逐渐完成、并发自然下降的尾段。“基线”指 C→B 单独运行时，取相对经过时间相对应的一段。它们不是同一时刻、同一批请求，存在状态与采样差异。

下面的吞吐来自每 5 秒采集的 vLLM 生成 token 计数器，不改写 AISBench 原生结果。延迟只纳入发送和完成都在窗口内的请求，可能漏掉跨越边界的慢请求，因此它是辅助比较，不能单独证明因果。

| 轮次 | B 的客户端方法 | B 同时接收 C 测试时的生成吞吐 | B 只接收 C 测试的基线生成吞吐 | 吞吐变化 | TTFT 变化 |
|---|---|---:|---:|---:|---:|
| 1 | 工具 | 438.22 token/s | 431.72 token/s | +1.51% | +24.85 ms |
| 2 | 原生 | 440.25 token/s | 435.33 token/s | +1.13% | -21.92 ms |
| 3 | 原生 | 434.07 token/s | 427.82 token/s | +1.46% | +17.30 ms |
| 4 | 工具 | 438.15 token/s | 435.33 token/s | +0.65% | +129.29 ms |

这四轮没有观察到 B 本机服务吞吐下降。但第 4 轮 TTFT 从 1,723.20 ms 增至 1,852.49 ms，增加约 129 ms（7.50%）；两边分别纳入 42 和 46 条完整请求，不能直接认定增量由 Runner 导致，也不能写成所有延迟完全不变。

## 工具增加了什么开销，为什么不能直接解释性能差？

请求路径是 **AISBench→目标 vLLM**，不是逐条经过网页、中心或 SSH 推理代理。网页读取日志不会让每个推理请求多经过一次中心转发。

但工具确实还有额外工作：连接检查、数据准备与缓存校验、启动进程、日志读取和结果收集。运行时适配还包括大数据集的 mmap 回退、单独设置预热输出长度、连接异常时唤醒等待以进入原生重试。本次对齐了数据与配置，预热输出相同、请求全部成功、数量吻合；未发现请求语义或重试数量的差别，但这不等于预先证明所有适配绝无性能影响。

| 资源观测 | 工具 | 原生 | 如何理解 |
|---|---:|---:|---|
| 整个前台步骤的客户端加 Runner 平均 CPU 核数 | 0.1306 | 0.1018 | 观测增量约 0.0288 个逻辑核；包括准备、启动、预热、执行与汇总，不是整机 CPU 使用率差。 |
| 正式推理期 Runner 及其子进程采样峰值 RSS | 33.53 MiB | 原生阶段 Runner 已暂停 | 不包含原生 AISBench 客户端全部内存。 |
| 包含连接、缓存检查等准备步骤的 Runner 采样峰值 RSS | 662.97 MiB | 不适用 | 是短时峰值，不代表正式推理全程占用。 |

CPU 核数 0.1 表示平均使用一个逻辑核的 10%。RSS 是驻留内存，可能包含共享页面，不能当成独占物理内存；上述资源观测不包含整个中心与浏览器，也不是纯粹隔离后的工具因果增量。

原生 AISBench 也需要 CPU、内存和网卡。两种方法在资源紧张时都可能影响同机 vLLM；本次资源余量下，没有证据显示新增控制工作造成了吞吐瓶颈。

**原因判断分三层：**

1. 已确认：工具存在额外控制与结果收集工作；实验测到了相应的资源消耗和运行结果差值。
2. 尚未确认：0.25% 或 4.75% 的吞吐差由这些工作造成。配置一致不代表服务调度、缓存分配和设备状态每轮完全相同，但本次没有定位到其中某项就是原因。
3. 因此能给出的影响范围：这组条件下，1,024 条单次配对观测到吞吐低约 0.25%；并行小批量两轮平均低约 4.75%，但重复波动使其不能视为固定工具损失。要测出可归因的稳定差异，还需更多交替重复和服务内部状态证据，不能靠当前数据补出一个确定原因。

## 指标只需这样理解

| 指标 | 意思 |
|---|---|
| 输出吞吐 token/s | 每秒产生多少输出 token，越高通常越好；不是每秒请求数。 |
| TTFT | 从发送请求到收到首个有效流式响应的等待时间，越低越好，包含排队、计算与传输。 |
| TPOT | 首个响应之后，按输出 token 数计算的平均生成耗时，越低越好。 |
| ITL | 该版本按相邻流式响应记录点计算的间隔；一块响应可能带多个 token，所以不一定等于 TPOT。 |
| E2EL | 一条请求从发送到完成的总耗时，越低越好。 |
| Benchmark Duration | AISBench 统计的正式测试阶段耗时，不等于从网页点击到看到结果的全部等待时间。 |

## 范围与收尾

本报告覆盖单向 1,024 条配对、追加并行的每方法两次 128 条对照，以及每方法一次无并行负载参照。最初计划中的全部双向互测没有执行，未算作通过。结果不能外推为高达 1,000 并发、128k 输入或更长输出下也相同。

实验结束后已恢复本次正常 Runner，确认空闲；专用临时环境完成归档后清理，正式工具结果保留。没有修改他人的容器、服务或任务结果。公开报告仅保留匿名拓扑、方法和指标，原始日志与复核材料由本地实验归档保留。
