# bench-web-plus 与原生 AISBench 同条件对照

实验开始日期：2026-11-07（Asia/Shanghai）。本报告覆盖优先执行的 1,024 条单向对照，以及追加的受控并行场景。未将最初尚未执行的双向互测算作通过。

## 先说明结论能证明什么

本次没有证明“Runner 包装 AISBench 会让推理变慢”。工具和纯原生组都由 AISBench 直接向 vLLM 发请求，中心负责提交任务和读取结果，不在逐条推理请求的数据路径中。配置、数据和 AISBench 源码相同，并不意味着两轮服务运行状态也完全相同。

- 1,024 条对照中，工具输出吞吐 447.9768，原生 449.1087 token/s，观测差值约 −0.25%；ITL 分别为 168.9 ms、167.7 ms。这是两次运行的差别，不能据此认定有固定的工具性能损失。
- 追加并行场景中，工具两轮平均吞吐 791.5853，原生 831.0672 token/s，观测差值 −4.75%。但原生自身两轮就有 881.2339 与 780.9005 token/s 的明显波动，工具两轮为 794.8768 与 788.2938。现有次数不足以分离运行波动与工具开销，不能将 −4.75% 写成 Runner 导致的下降。
- A 服务和 B 本机服务需要分开看：B→A 这一路没有观察到 B 本机承受测试负载后吞吐降低；C→B 这一路在重叠窗口也没有观察到吞吐降低。但第 4 轮 B 的窗口 TTFT 比基线高约 129 ms，不能说所有延迟完全不受影响。后文列出比较边界。
- 能直接量到的是客户端与 Runner 的资源消耗：整个前台步骤两者平均 CPU 合计，工具 0.1306 核、原生 0.1018 核，观测增量 0.0288 核。工具正式推理期 Runner 及子进程峰值 RSS 33.53 MiB；连接/缓存检查等整个步骤峰值 662.97 MiB。这些是资源成本，不等于对 vLLM 吞吐造成了同等比例损失。

客户端为 `80.5.9.127`，目标为 `80.5.9.145:19300`。两轮均预热 5 条成功、正式请求 1,024 条成功、失败 0；正式输入/输出均为 16,384/1,024 tokens。

| AISBench 原生指标 | 工具组 | 原生 CLI | 工具相对原生 |
|---|---:|---:|---:|
| Benchmark Duration | 2340692.824 ms | 2334793.186 ms | +0.253% |
| Output Token Throughput | 447.9768 token/s | 449.1087 token/s | -0.252% |

### ITL、TPOT 与这次差值的含义

用户所说的“LTL”在这里按 AISBench 的 **ITL** 对照，表内保留原生汇总值。TTFT 是首个有效响应的等待时间；TPOT 是首个响应之后的生成耗时除以输出 token 数减一；该版本 ITL 取首个有效响应之后相邻记录时间点的间隔。流式响应可能一次包含多个 token，因此 ITL 与 TPOT 不必相等，不能互相替代。

1,024 条对照的 ITL 为工具 168.9 ms、原生 167.7 ms，差 1.2 ms（约 +0.72%）。追加前台四轮 ITL 为 46.6、43.6、50.5、48.6 ms；工具平均 47.60 ms，原生平均 47.05 ms，观测差约 +1.17%。ITL 与吞吐并不是同一个指标：首 token 等待、请求排空和请求之间的调度同样影响总吞吐，不能从某一项的差值直接推算另一项。

尚未用服务内部调度、缓存分配、设备频率等证据定位两种方法之间差值的来源。本次不把缓存、网络或 Runner 中的任一项当作已经证实的原因。对照独立隔离每轮 cache_salt，未清空服务缓存；它也不能使不同运行的所有底层状态完全相同。

- 原生组暂停已确认空闲的本次 Runner 执行进程，用独立 Python 环境直接执行官方 AISBench CLI，不加载工具的 `sitecustomize` 或 `aisbench_runtime`。SSH 管理、TLS 管理入口及只读采样保留。

### 对两台 vLLM 服务分别意味着什么

**A（128）是被 B 测试的目标服务。** 上面的无后台/有后台比较测到的是 B→A 整条路径：工具吞吐 769.6345→791.5853 token/s，原生 804.8254→831.0672 token/s，均没有下降。它支持“在本次资源余量下，B 本机 vLLM 被测时，没有观测到 B 的客户端拖慢对 A 的测试”，但不能证明 A 的内部性能在所有条件下完全不变，也不能把小幅上升解释成并行测试有益。

**B（145）是运行客户端、同时又被 C 测试的本机服务。** 下面用 C→B 的指标判断 B 是否被本机客户端挤占。重叠窗口 B 生成吞吐相对无前台客户端基线为 +0.65%～+1.51%，未观察到吞吐损失；TTFT 有波动，其中第 4 轮增加约 129 ms（7.50%）。窗口请求集合和数量不同，不能把这个延迟增量直接判定为 Runner 的因果影响。上面的后台整轮表另保留原生 TTFT、TPOT、ITL，整轮包含非重叠时段，不能拿它代替窗口比较。

客户端会使用本机 CPU、内存和网卡；原生 AISBench 也会使用这些资源。两者都可能在资源紧张时影响本机 vLLM，而本次 B 的平均 CPU 使用率约 8.6%～9.0%、最低可用内存约 1,830 GiB，客户端未分配 NPU。这次未观察到资源争抢导致吞吐下降，不能推广为高并发、长输出或主机资源紧张时也绝无影响。

## B 本机服务在重叠时段的辅助观测

### 先看懂这段在比较什么

这里要回答的问题是：**145 上运行客户端去测 128，会不会挤占资源，拖慢 145 自己的 vLLM？**

```text
B：145 的 Runner / 原生 AISBench ──→ A：128 的 vLLM
C：127 的原生 AISBench          ──→ B：145 的 vLLM
```

两行代表两个独立任务，同时进行。145 既是第一行的“发请求机器”，也是第二行的“接请求机器”。本节主要观察第二行，判断 145 自己的服务有没有受影响。

| 文中概念 | 在这次实验中的意思 |
|---|---|
| A / B / C | A=80.5.9.128，B=80.5.9.145，C=80.5.9.127；字母是机器代号，不表示性能等级。 |
| 服务 / 客户端 | vLLM 服务接收请求、运行模型；AISBench 客户端发送请求、记录响应。Runner 负责启动和管理客户端任务。 |
| 前台任务 | B→A，也就是 145 去测 128。本报告比较它使用工具和原生 CLI 时的区别；与窗口是否在屏幕前台无关。 |
| 后台任务 | C→B，也就是 127 去测 145，用来模拟另一个人正在测试 145 的服务。这里也是正式推理负载，不是空闲后台进程。 |
| 基线 | 用作参照的测试。本节基线为 C→B 单独运行，B 没有同时执行 B→A；前一节的“无后台基线”则是 B→A 单独运行。两种基线观察的方向不同。 |
| 重叠时段 / 窗口 | 两路都在发送正式请求时，选出的一段比较时间；本次还避开后台最后排空阶段。窗口秒数就是这段时间有多长。 |
| 排空阶段 | 最后一些请求已发出，正在等它们完成；已完成的请求不再补充，实际并发通常逐渐减少，吞吐可能自然下降。 |
| 匹配基线窗口 | 从单独运行的基线中，取相对测试进程的经过时间相对应的一段作比较，不是同一时刻重做，也不是完全相同的服务运行状态。 |
| 辅助观测 | 根据服务计数器、逐请求时间和资源采样额外计算的数据，用来帮助判断影响；不是 AISBench 原生新增了一种测试模式。 |
| 完整落在窗口内的请求 | 发送和完成都在所选时间段内的请求。跨过窗口边界的请求不进入该表的延迟平均值，因此两边纳入的请求数量可能不同。 |
| 选样 / 边界偏差 | 例如一个特别慢的请求直到窗口结束仍未完成，就不会进入“完整请求”平均值；所以窗口平均延迟不代表全部请求，也不能单凭它认定原因。 |
| 采样与插值 | 每 5 秒读取一次计数器；窗口边界落在两次读取之间时，估算边界计数，所以吞吐有采样误差。 |

### 表格里的指标怎么读

| 表格指标 | 通俗解释与读法 |
|---|---|
| B 生成 TPS | 145 的 vLLM 每秒生成多少个输出 token。这里 TPS 指 token/s，不是每秒请求数。由窗口内生成 token 的增量除以秒数得到，越高通常表示吞吐越大。 |
| 基线 B 生成 TPS | 没有 B→A 客户端负载时，145 服务对应基线窗口的生成速度。 |
| 相对变化 | （同时运行数值÷基线数值−1）×100%。吞吐为负表示比基线低；延迟为正表示比基线更慢。小幅差值也可能来自运行波动。 |
| TTFT | 请求发出后，到客户端收到首个有效流式响应要等多久，单位 ms，越低越好。它包含排队、模型开始生成、传输等等待，不能直接当成纯网络延迟。 |
| TPOT | 收到首个响应之后，平均每个输出 token 花多少时间，单位 ms，越低越好。按该版本 AISBench 的公式计算，不是某一个 token 的独立实测时间。 |
| ITL | 相邻流式响应记录点之间的间隔，单位 ms；一个响应块可能带多个 token，因此不一定等于 TPOT。本节窗口表没有重新计算 ITL，上面的原生整轮表保留 ITL。 |
| E2EL | 一条请求从发送到响应结束的总耗时，包含首个响应等待和后续输出时间，越低越好。 |
| 平均 CPU 核数 | 进程 CPU 时间÷观测秒数。例如 0.10 核，相当于观测期间平均使用一个逻辑核的 10%，不是整台机器 CPU 使用率 10%。 |
| 宿主机平均 CPU 使用率 | 整台机器全部逻辑核合计的平均使用比例，与上一行“某组进程用了几核”口径不同。 |
| Runner 峰值 RSS | 窗口内采到的 Runner 及统计范围内子进程驻留内存峰值。MiB 是内存单位；共享页面也可能计入，不是独占内存的精确值。 |
| 客户端峰值 RSS 合计 | 所统计客户端进程的 RSS 相加后取采样峰值；共享页面可能重复计数，不能当成实际物理内存增量。 |
| 最低可用内存 | 所选时间段内采到的宿主机最低可用内存，不是 Runner 占用量。GiB 也是内存单位，1 GiB=1,024 MiB。 |
| RX / TX Mbps | 所统计网络接口接收/发送的速率，单位为每秒百万比特。可能包含其他流量，不等于 AISBench 独占带宽，也不覆盖所有 NPU 互联流量。 |

**第一张表看吞吐有没有掉。** 例如第 1 轮：同时运行为 438.22 token/s，基线为 431.72，相对高 1.51%。只能说这次没有观察到吞吐下降，不能说 Runner 提高了服务性能。

**第二张表看等待有没有变长。** 例如第 4 轮：同时运行 TTFT 为 1,852.49 ms，基线为 1,723.20 ms，相差约 129 ms（7.50%）。它们分别纳入 46 和 42 条完整请求，存在上面解释的选样差异，所以不能直接判定这 129 ms 就是 Runner 引起的。

**后两张表看本机资源是否紧张。** “整个前台步骤”还包括连接检查、缓存检查、启动、预热、正式请求和汇总，比只看正式请求的时间段更长。因此，准备阶段可能出现较高内存峰值，不能把它理解为正式推理全程持续占用这么多内存。

## 解释与范围

工具也不只是静态地传递参数：还负责准备/校验数据、启动子进程、收集日志与结果，并加载运行时适配，包括大数据集共享内存不足时的 mmap 回退、单独的预热输出长度，以及连接异常时唤醒等待以进入原生重试。这些适配与原生源码分别审计；本次正式数据和模型配置对齐，预热输出均为 1,024，所有请求成功，服务请求数符合正式加预热数量，未观察到额外请求。没有证据将本次差值定位到这些适配，但也不应仅凭“内部用了 AISBench”就预先断言工具绝无开销。


Runner 额外成本主要来自控制进程、任务与日志管理；实际模型请求由 AISBench 客户端直接发往目标服务，不逐条经过中心 SSH 隧道。原生 AISBench 同样需要客户端 CPU、内存和网络，这部分不能全部算成工具新增开销。对本机 vLLM 的影响应同时看 CPU、内存、网卡余量和实测服务吞吐，不能仅由“同机运行”判断。

本次是一个 1,024 条顺序配对与每方法两次 128 条重复，并不构成统计显著性结论；不能直接外推到 128k/220k 输出或 1,000 并发。背景整轮原生结果与窗口辅助观测分开保留，避免把前台结束后的后台尾段当作重叠负载。网卡统计来自内核接口，未完整覆盖 NPU 设备间互联。

## 安全与收尾

没有停止、重启或修改其他人的容器和 vLLM 服务，没有清理共享服务缓存。原生阶段只暂停已确认空闲且登记归本工具管理的 Runner 执行进程，结束后恢复。实验中另建的 58 临时 CPU Runner 已删除，原 7 台登记保持；废弃的专用准备目录已清理。当前报告不会将未执行的双向互测标为完成。

工具完整日志与配置保留在对应 Runner 的正式任务目录；本机保存官方指标、原生阶段日志、逐请求分析与资源采样。本报告只提交结果与必要配置，不包含登录凭据、Runner token 或用户会话 cookie。


计时边界补充：工具从提交任务 API 到观察到结果完成为 2417.25 秒；原生命令执行为 2399.59 秒。两者观察差值为 17.66 秒，包含任务检查、原生启动与汇总、工具收集及最长约 5 秒的轮询等待，起止边界不同，不能把该差值全部当成推理开销。
